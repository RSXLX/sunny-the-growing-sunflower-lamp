# BLOOM MVP 总体规划 v2

日期：2026-09-22。本文整合此前产品、代码评估与 Tripothon 研究，作为建议的统一规划入口。旧报告保留用于查证；范围或优先级冲突时，后续讨论以本版建议为基础。本文是规划交付，不代表用户已确认所有产品取舍，也不代表开始执行采购、付费生成、开发或报名。

## 1. 产品定义

**BLOOM：一盏能把生活记忆变成可更换外装的台灯。**

参赛表达：**A Gift for Your First Room — 送给你的第一间房，让生活慢慢长出自己的形状。**

首批用户聚焦刚搬家、开始独居、希望通过个人物件布置房间的人。核心体验是本人为自己的房间创作，也可以由朋友提供照片/祝福参与创作。MVP 不加入跨账号赠送设备、物流或所有权转移流程。

核心价值：一个耐用的灯体，可以承载不断增加的个人创作。Tripo 将用户选定的视觉意象变成装饰几何；BLOOM 把它接到可制造结构、实物档案和点亮体验上。

## 2. MVP 要验证的三个假设

1. 用户愿意把具体记忆变成灯上的外装，且愿意在完成第一件后继续创作。
2. 一件真实 Tripo 生成结果能在可接受的人工修正工作量内，适配统一接口、打印并装到灯上。
3. 用户能理解外装、故事和实际灯光之间的关系，实际使用流程足够顺畅。

验证方式：建议邀请 3–5 位目标用户完成概念选择与软件流程，记录他们选择什么、哪里需要解释、是否愿意再创作。记录至少一件实体外装的生成次数、人工修正时间、制造成本、打印结果和安装过程。样本仅用于早期方向判断，不宣称市场验证或商业规模已成立。

## 3. 完成交付的具体样子

参赛核心版交付：

- 1 盏真实可工作的台灯：主照明、实体开关/调光、必要故障保护。
- 2 件能在同一接口安装的外装：默认向日葵 + 1 件由真实 Tripo 生成并经工程修正的记忆外装。
- 2 个与实物对应的可读写标签；装配后能识别外装，读取配置，并显示对应的故事入口。
- 1 套可在电脑/手机浏览器操作的工作台：记忆、创作、试装、制造、安装记录。
- 1 条可追溯证据链：输入、实际生成任务、原始模型、修正文件、最终制造版本、实物照片、安装事件。
- 1 份可复现运行说明、1 段完整演示录制和1份视觉素材板。

核心成功标准：第二个人可以理解并操作软件；演示的外装确实来自展示的生成任务，并且可以在真实灯上安装、识别和点亮。

范围调整说明：前版把两路调光写为必须，本版建议以主照明闭环为必交付，把独立分体投影的实物演示设为条件增强。保留现有第二路软件/固件能力；不把尚未通过台架验证的投影列为对外承诺。如果用户坚持以“房间光影变化”为核心卖点，则投影应恢复为 P0，并相应缩减分享、视觉美化等工作。

## 4. 用户完整流程

| 步骤 | 用户操作 | 产品反馈 | 工程或人工动作 |
|---|---|---|---|
| 记下 | 写一段文字，或选一张照片作为参考 | 私人记忆卡片 | 本地保存；私密内容默认不发给第三方 |
| 选形 | 选择希望保留的主体，填写描述或上传参考图 | 显示即将发送的图/文字，用户确认 | 图片缩放、格式检查；支持简单裁切即可 |
| 生成 | 选文字或图片方式并确认可能的费用 | 排队、生成、失败/待核实等真实状态 | 服务端调用 Tripo，保存任务和输入快照 |
| 试装 | 查看实际模型，选择方向和比例 | 原稿与灯体上的适配草案对照 | CAD 载体组合，人工检查和修正 |
| 制作 | 选择通过审核的制造版本，下载制造包 | 显示制作进度与需完成的检查 | 操作员切片、打印、后处理并回填证据 |
| 安装 | 将外装固定到灯上并完成标签绑定 | 设备读回确认，展示当前外装 | NFC 写入验证、安装识别、配置应用 |
| 留存 | 查看故事和制作过程，选择是否公开设计 | 成长时间线 | 默认私有；公开时单独确认描述和设计 |

首版是有人参与的制造服务流程。用户自己操作创作和使用，制作人员负责实际工程审核与打印。界面明确等待人工处理，不虚构自动制造。

## 5. 功能范围与优先级

### P0：核心版必须完成

| 模块 | 保留或新增内容 | 验收要点 |
|---|---|---|
| 我的房间 | 真实设备状态、开关/亮度、当前外装、故事入口 | 状态依据设备回执；显示真实/模拟和离线差异 |
| 成长记忆 | 现有文字记录；新增可选参考图片 | 私有隔离；发送给 Tripo 前确认具体内容 |
| 外装工作室 | 文生模型、图生模型、实际资产预览、任务恢复 | 至少一种确定的模型配置经真实验证；两种输入路径可操作 |
| 试装 | 使用真实生成模型叠加灯体；原稿/适配稿切换 | 方向与比例可确认；不拿固定样例替代结果 |
| 我的衣橱/制作 | 制造版本、修正版导入、审核、制作记录、标签绑定 | 实物固定引用已批准版本，文件更新需新版本 |
| 硬件联调 | 设备凭据、命令/回执、按键、NFC、故障状态 | 全板构建、烧录和实测；关键故障不依赖网络处理 |
| 数据与运行 | SQLite 迁移、资产存储、备份恢复、日志 | 升级不破坏旧数据；重启后能恢复已知生成任务 |

“图生模型 P0”指支持一条简洁可用的图片输入流程，不包含复杂图片编辑器、自动照片理解或多图一致性系统。实际生成模型选型根据小样联调结果确定，不预先把最新版本等同于最适合制造。

### P1：核心闭环完成后增强

- 复用现有公开设计与二次创作流程，完成两个账号的演示。现有权限隔离测试持续保留，不因优先级后移而放弃隐私边界。
- 分体投影台架通过后，完成一个可用图案及手动换片演示。
- 第三套星夜外装、视觉润色、更完整的成长时间线。
- 将手动修正流程中重复出现的几何操作自动化。

### 首版不做

自动机械生长、追踪转头、语音助手、摄像头、RGB、多电池供电方案、自动换片、任意生成图案自动投影、支付物流、复杂社区、原生手机 App、公网多租户运营和自动控制打印机。

## 6. Tripo 的核心角色与集成方式

### 三层分工

| 层 | 负责什么 | 交付 |
|---|---|---|
| Tripo | 根据确认后的视觉输入生成装饰形态 | 原始模型、任务 ID、实际模型版本和输入参数 |
| BLOOM 制造适配 | 尺寸/方向处理、固定接口组合、检查与修正版管理 | 可供人工审批的制造候选版本 |
| 实物与设备 | 制造、安装、识别、照明、使用记录 | 与版本对应的实体实例和事件 |

主流程建议采用“确认参考图 → 图生模型”；文字生成作为另一种入口。参考图可来自照片裁切或手绘，首版不增加额外图像生成供应商。

### 技术任务

1. 为现有 provider 增加图片上传和 image-to-model 路径；在服务端限制文件格式/大小、验证内容，保存输入快照。
2. 用真实输出选择稳定的模型与参数组合；验证压缩格式、坐标、三角网格及尺寸，不只改 model_version。
3. 将生成、下载/转换、制造审批作为可区分阶段。生成成功不直接标记为可打印。
4. 为文字、图片、任务、原稿与派生版本建立关联。未知提交停下等待核实，不自动再次产生付费提交；已知任务优先恢复查询。
5. 原稿保留不覆盖。模型转换使用受限子进程或经验证的供应商转换路径，记录失败原因。
6. 对适配结果提供预览；人工检查连通、薄弱连接、壁厚、支撑需求和配合界面。首件允许建模工具手工修正。

已有自动压扁到指定深度并裁切的方案仅作草案生成器。最终参数按实际设计审核，不把固定压扁当作通用制造算法。

参考能力由 9 月 22 日已核对的官方资料支持，账户权限与实际输出仍需联调：[图生模型](https://docs.tripo3d.ai/model-generation/image-to-model-v3-0-v3-1.html)、[文生模型](https://docs.tripo3d.ai/model-generation/text-to-model-v3-0-v3-1.html)、[格式转换](https://docs.tripo3d.ai/export/conversion.html)。

## 7. 软件实现规划

继续沿用现有浏览器前端、Python 服务、SQLite、文件资产和 ESP32 协议。核心版以本机/可信局域网演示为运行目标，单服务进程。暂不重写框架、不增加微服务。

### 页面组织

保留现有六页。用户主要路径为“房间 → 记忆 → 工作室 → 衣橱 → 房间”。工程检查放在衣橱的制作详情，设备诊断留在硬件页；交换花园不作为首次使用的必经步骤。

### 最小数据扩展

| 对象 | 关键数据/约束 |
|---|---|
| 输入资产 | owner、文件路径、类型、哈希；与私有记忆关联；记录用户确认发送的输入 |
| 生成任务 | provider task_id、输入快照、模型/参数、状态、失败原因、时间；沿用现有幂等策略 |
| 制造版本 | design_id、版本号、原稿/派生文件、哈希、接口版本、审核状态与记录 |
| 实物实例 | 固定制造版本、制作状态、材料与实际尺寸记录、照片、NFC 标识 |
| 安装事件 | 设备、实例、时间、实际/模拟来源和稳定事件 ID |

实现时可复用现有 designs 字段，避免为每个概念都新增服务或表。制造版本需不可变：修改模型或关键制造参数生成新版本；已绑定实物继续引用原版本。

建议制造状态：候选 → 待审 → 已批准 / 需修改；实物状态：计划 → 制作中 → 已打印 → 装配验证 → 已绑定。打印失败保留失败记录，可重新制作；安装/移除是事件，不改写制造事实。状态设计实施前统一前后端约定。

迁移使用版本脚本和备份；测试覆盖旧数据升级、模型更新后审核失效、跨用户访问、文件导入验证、真实实例不能引用未批准版本。

### 主要开发入口

- `app/providers.py`：图片生成、模型参数和任务调用。
- `app/service.py`：生成/制造状态、版本审核、导入、绑定关系。
- `app/store.py`：最小迁移与字段扩展。
- `app/geometry.py`：模型格式验证、适配与检查。
- `web/app.js`、`web/viewer.js`：输入确认、实际模型试装、版本和制作详情。
- `hardware/firmware/`：真实设备构建、离线与回执验证。

## 8. 硬件与制造规划

优先复用当前灯体和三螺丝压环接口，先按实购物料测量后定版。

| 子系统 | 核心工作 | 前置门槛 |
|---|---|---|
| 控制与供电 | ESP32、驱动、按键、供电保护、接线与固定 | 台架电气检查后才装壳 |
| 主照明 | 实际 LED、扩散片、热源监测及可靠保持结构 | 分阶段通电记录、故障关闭验证 |
| NFC | PN532 固定位置、标签布局、写入/读回、识别 | 实际灯体和材料环境下测读距与成功率 |
| 结构 | 底座、杆、灯头、外装接口、配重和紧固 | 实测尺寸→配合试片→完整零件 |
| Tripo 外装 | 原稿修正、接口适配、打印、安装 | 通过制造版本审核后输出制造包 |
| 条件增强：投影 | 灯板/镜片/插片台架、支架和保持件 | 光学实测和独立热源保护方案通过后装机 |

包内已知的扩散片、镜片、灯板固定及支架问题必须落实到结构；原图的通用文字不能代替可装配设计。主灯与分体投影若同时使用，分别评估实际温升和保护覆盖。

打印顺序：配合试片 → 默认外装/接口装配 → AI 外装 → 其余外观件。预留一次返工；记录材料、机器、方向、后处理与尺寸结果。HeyGears 使用与否取决于实际制造资源，不在未落实前承诺工具赛道资格。

## 9. 实施顺序与人员分工

建议至少两条工作线推进，以下为人类团队职责规划，不是自动创建并行代理：

- 软件负责人：Tripo、数据/任务、前端试装、制造版本、测试和运行。
- 硬件负责人：物料、测量、固件、台架、结构修改与整机验证。
- 打印支持：切片、试片、制造和后处理，可由硬件负责人或外包承担。
- 产品/展示负责人：用户故事、体验测试、素材和提交，可由软件负责人兼任。

必须优先完成的两个验证：真实 Tripo 输出能进入制造链；实际接口和灯体可用。软件装饰、社区和第三套外装后移。

关键路径：账户/工具链与实物尺寸 → 真实模型/配合试片 → 工程修正 → 打印 → 装配/NFC → 整机回归 → 演示提交。

## 11. 验收与证据

| 维度 | 核心版通过标准 |
|---|---|
| 产品 | 一条真实记忆/视觉输入到真实外装的完整故事；3–5 位试用者反馈有记录，问题已分级 |
| Tripo | 至少一个真实任务的最终模型完成制造；文字/图片入口按实际模型合同验证；刷新不重复提交，未知结果停止重试 |
| 模型 | 原始资产和制造版本可区分；固定接口适配与人工修正可追溯；未审核版本不进入实物制作 |
| 制造 | 默认外装与 AI 外装均能安装；记录制造条件、尺寸、固定检查和实拍 |
| 设备 | 20 次换装至少 19 次识别成功；重复读取不重复记录同一安装；未知标签有明确反馈 |
| 离线/故障 | 断网仍可本地操作；过期命令不延迟执行；传感器异常和规定故障触发关闭；重启状态有实测 |
| 数据 | 私有记忆隔离；公开设计不带私人原文；备份恢复后模型、版本和实例关系一致 |
| 浏览器 | 原生 HTTP 页面、模块、会话、下载与实际模型展示通过；目标手机宽度正常；不以旧截图代替 |
| 展示 | 可体验 Demo、流程录制、视觉素材板；真实/模拟/人工步骤明确，打印片段对应同一任务与实物 |

不在本规划中臆定材料温度、公差和运行安全阈值；这些由硬件负责人依据实购物料、材料资料和台架结果确定并保存。数字测试不替代实体测试。

## 12. 资源、预算与风险控制

启动资源：Tripo 可用账户及明确调用预算、ESP32/PN532/LED/驱动/传感器等样件、基本测量和焊接工具、打印/后处理渠道、至少一次返工窗口。

预算不提供未询价的总金额。分别记录电子件、结构光学件、试片、完整打印、返工、API、运费与外包；真实生成次数有上限，先用少量样例验证，不批量盲试。

| 风险 | 提前检查 | 应对 |
|---|---|---|
| 生成结果不适合制造 | 前两天真实样例 | 收敛形态，允许人工修正；保留 Tripo 原稿证据 |
| 模型格式不兼容 | 检查真实返回资产 | 经验证的转换路径；失败明确显示，禁止静默替换演示模型 |
| 打印/安装失败 | 实测尺寸和试片 | 固定一种接口，留一次返工，延后第三套外装 |
| 投影效果不成立 | 独立光学台架 | 不进入核心版承诺，优先完成主灯 |
| 设备不稳定 | 尽早板级联调 | 先验证本地控制与保护，再接网络；不以模拟回执冒充 |
| 参赛资格不明确 | 查提交表/向主办方核实 | 明确既有代码与新增贡献、工具证据、实体交付规则 |

## 13. 第一轮应执行的工作

1. 统一开发环境和独立测试数据，复现现有软件基线。
2. 选定一个具体故事和参考图，做一次小规模、预算明确的 Tripo 资产验证。
3. 确认硬件执行人、关键样件和打印安排，完成现有固件全量构建。
4. 同时推进制造版本最小方案与实购物料接口测量。
5. 根据真实生成、接口试片和台架结果锁定可交付外装及时间表。

本规划的优先目标是交付一个真实、可重复操作的“记忆变成灯上外装”的体验。达到这一目标后，再扩展房间光影、外装数量和创作者之间的交流。
